# pi5 soak (Phase 4), 2026-11-05

**Done 2026-11-05 on `pi-exit-relay1-tor-ce`, for Phase 4 of [flavors.md](flavors.md#rollout).** It ran the draft release `pi5-v6.18.60-hardened1` (CI run 4374) for one day against the stock Raspberry Pi kernel on a production Tor exit relay, and A/B-tested the hardening trades listed in [Performance](flavors.md#performance). The relay is back on stock, and `/boot/firmware` is byte-identical to before the soak.

## Results in brief

| Question | Answer |
|---|---|
| Stability | No incidents. 5 reboots, 4 confirmed trial boots with `verify` fails=0, no `macb` TX timeouts or other kernel errors, no softnet or NIC drops. |
| Tor CPU per relayed byte | **+11%** on hardened: 26.1 → 29.0 s of Tor CPU per GB at 4 MB/s (95% interval +7% to +16%). |
| Kernel network path | **+32% per frame** (7.5 → 9.9 µs); +1.3 points of one core at 6 kpps (+29%). |
| CPU0 softirq | 2.4% of CPU0 on stock and 3.5% on hardened at 34–36 Mbit/s. 90–93% of all softirq time and 99.97% of NET_RX run on CPU0. Not a limit yet (see [CPU0 and RPS](#cpu0-and-rps)). |
| EEPROM | A real `rpi-eeprom-update -f` from the hardened kernel flashed and verified, and the next boot ran the image it wrote. |
| `init_on_free=0` | No gain: −1% (interval −7% to +5%). It only moves the zeroing from free to allocation. **Keep `init_on_free=1`.** |
| `preempt=lazy` | No gain in the kernel path (+1%), and Tor used 5% *more* CPU per GB (+1% to +9%). **Keep full preemption.** |
| `DEBUG_LIST=n` | At most ~0.4% of busy CPU (estimate from profiles). **Keep `DEBUG_LIST=y`.** |

The hardened kernel costs real CPU here, but the relay is far from CPU-bound. At 34–36 Mbit/s the whole relay used 0.15 of its four cores on stock and 0.18 on hardened. **Recommendation: Phase 5 can go ahead with the kernel and the intent configs as they are.** None of the three trades buys enough speed to give up its protection.

## What ran

- **Relay:** Raspberry Pi 5, Raspberry Pi OS (trixie), SD-card root, RP1 `macb` Ethernet at 1 Gbit/s. Tor 0.4.9.15, upgraded to 0.4.9.16 during the soak (see [Timeline](#timeline)). One Tor instance (`tor@23.191.200.2_443`) with about 5,000 established TCP connections. eth0 runs `fq`; RPS is off, so all NET_RX softirq runs on CPU0. node_exporter, alloy, wazuh-agent, bird, unbound and tailscaled run alongside.
- **Stock:** `6.18.50+rpt-rpi-2712`, Raspberry Pi's packaged kernel.
- **Hardened:** what the pi5 meta package would pull in, from the draft release's assets (hashes checked against `manifest.json`):
  - `linux-image-6.18.60-hardened-unredacted-pi5` (Raspberry Pi's 6.18.60 + anthraxx `v6.18.60-hardened1`);
  - `unredacted-rpi5-boot`;
  - `unredacted-hardened-defaults` from the latest amd64 release (`7.2.15-hardened0~fwd7.2.10.1`).

  No `-dbg` package. The kernel booted only as a confirmed trial (`try`, `reboot '0 tryboot'`, `verify`, `confirm`), never with `promote`, so every reboot fell back to stock.
- **CVE-2026-98432 mitigation:** runtime-only, so re-applied right after each of the five boots. The collector checked it every 2 minutes: 0 samples without it.

## Method

One day does not allow whole-day windows per kernel, so the windows are interleaved, each 4 hours, with stock at both ends:

| Window | Kernel | Command line extras | UTC | Boot |
|---|---|---|---|---|
| S1 | stock | — | 01:56–04:00 | `6b79054a` (already up 1.9 h) |
| H1 | hardened | — | 04:00–08:00 | `dce29628` |
| T1 | hardened | `init_on_free=0` | 08:00–12:00 | `62f00a2b` |
| T2 | hardened | `preempt=lazy` | 12:00–16:00 | `0dd849ce` |
| H2 | hardened | — | 16:00–20:00 | `5762e9c8` |
| S2 | stock | — | 20:03–02:00 (+1 day) | `8b1b263c` |

All hardened boots also had `panic=10`. S1 vs H1 and H2 vs S2 compare the kernels at adjacent times of day; H1 and H2 bracket the two trades, so each trade is compared with the hardened baseline at its own time (linear interpolation between H1 and H2).

**Collection.** A temporary systemd timer sampled every 2 minutes into `/root/phase4` (removed after the soak):
- `/proc/net/dev`, `ethtool -S eth0` (frames), `tc -s qdisc`;
- the Tor unit's cgroup `cpu.stat` (user and system µs);
- `/proc/stat` per CPU (user, system, irq, softirq), `/proc/softirqs`, `/proc/net/softnet_stat`, eth0's interrupt counts;
- TCP counters, socket counts, conntrack, load, temperature, CPU frequency, `/proc/meminfo`;
- hourly `/proc/slabinfo` and `/proc/interrupts`; once per boot, the command line, lockdown, LSMs, preemption mode, qdisc, RPS mask, coalescing and bootloader timestamps.

A second unit appended the whole journal to disk, since journald on this relay is volatile. Once per window, `perf record -a -g -F 99` for 180 s (Raspberry Pi's `linux-perf` 6.18.50, removed afterwards); on the hardened kernel `kptr_restrict` was set to 0 only for the recording and the report, then put back to 2.

**Analysis.** Consecutive samples on the same boot form 2-minute intervals. Excluded:
- the first 30 minutes of every boot;
- the perf recordings and other step scripts;
- 30 minutes after Tor was restarted by the package upgrade in T1.

The metrics:
- **Tor CPU per relayed byte**: the Tor cgroup's CPU time over eth0 bytes (in plus out).
- **Kernel network path**: Tor's system time (its send/receive syscalls, and transmit down to the driver) plus all softirq time on all CPUs (receive, transmit completion, timers). Per frame and per GB.
- **CPU0 softirq share**: softirq time on CPU0 as a share of CPU0, and of all softirq time.

Traffic changes with the time of day, and fixed costs (timers, monitoring) spread over fewer bytes when traffic is low. So the comparison does not rest on window averages: for each window, a least-squares line of CPU rate against traffic rate across its intervals gives the cost at a common traffic level (packet rate for the kernel path, throughput for Tor). Each window's traffic spanned the reference levels. 95% intervals come from a bootstrap over 20-minute blocks.

Together they are about 3% of all samples on H2, about 4.5% of busy samples. That is about a third of the hardened kernel's extra CPU: H2 used 13% more busy CPU per GB than S2. The rest has no symbol of its own: the stack protector, the shadow call stack, `ZERO_CALL_USED_REGS` and the stack erase on syscall exit are compiled into every function. `memset` is about the same on both kernels (0.45–0.70%). Its callers, such as seccomp filtering, nftables, socket setup and `inet_diag` dumps, run on both.

### The trades

**`init_on_free=0`** (T1): kernel path −0.06 points at 6 kpps (−1%, interval −7% to +5%); Tor CPU per GB +2% (−5% to +8%). The profile shows why there is no gain. With `init_on_free=1`, the kernel zeroes objects when they are freed and linux-hardened checks them with `memchr_inv` when they are reused. Mainline skips zeroing on allocation in that case. With `init_on_free=0`, `memchr_inv` drops to zero, and `init_on_alloc=1` zeroes on allocation instead (`memset` 0.62% vs 0.45%). The cost moves from reads to writes; it doesn't go away. The trade would give up two things for nothing:
- freed data no longer cleared at once;
- the use-after-free write check.

**Recommendation: keep `init_on_free=1`.**

**`preempt=lazy`** (T2; dmesg `Dynamic Preempt: lazy`): kernel path +0.07 points at 6 kpps (+1%, interval −4% to +5%); context switches unchanged (4,417/s vs 4,176–4,439/s). Tor CPU per GB went *up*: +1.6 s, or +5% (+1% to +9%). That is a single window, and Tor latency wasn't measured. Either way, nothing here favours lazy preemption. **Recommendation: keep full preemption, and keep `PREEMPT_DYNAMIC`**, which costs nothing measurable and lets `preempt=` be changed at boot.

**`DEBUG_LIST=n`**, keeping `LIST_HARDENED=y`: not tested at runtime, because it needs a rebuild. It is estimated from the profiles: `__list_del_entry_valid_or_report` and `__list_add_valid_or_report` take 0.20–0.26% of all samples, 0.3–0.4% of busy samples.
- **Upper bound on the saving:** `LIST_HARDENED` alone would still run inline checks on the same list operations, so the real gain is below that.
- **Why not the upstream +7%:** that figure is netperf on a Clang build, where list operations are a far larger share of the work than on this relay.

**Recommendation: keep `DEBUG_LIST=y`.**

### CPU0 and RPS

Softirq time on CPU0 grows with traffic:

| | CPU0 softirq per 1,000 frames/s | CPU0 all softirq at |
|---|---|---|
| Stock | 0.39% of CPU0 | ~260 kpps |
| Hardened | 0.50–0.53% of CPU0 | ~190 kpps |

The right column is a linear extrapolation. At today's 680–700 bytes per frame, 190 kpps is about 1 Gbit/s of combined in + out traffic, about 30 times today's. RPS isn't needed at this load, on either kernel. Revisit it if CPU0 softirq passes ~25%.

### TX timeouts and drops

- **TX timeouts:** none on any of the six boots. No `NETDEV WATCHDOG`, `macb` errors, softnet drops, or NIC rx/tx drops.
- **`fq` drops:** both kernels had them. Counted windows saw 39 in H1, 118 in T2 and 268 in S2 (stock). S2's breakdown: 45 `flows_plimit` (the per-flow limit of 100 packets) and 223 `horizon_drops` (packets timestamped more than 10 s ahead). These are fq's own limits, not stalls.

### Other observations

- **Unreclaimable slab:** about 148 MB on hardened against about 80 MB on stock. This comes from no slab merging, canaries, randomized kmalloc caches and buckets. The relay has 8 GB.
- **Conntrack:** 6–10k entries on both kernels, with bursts to 14–34k. Bursts happened on both, with no step at the kernel switches; the hardened windows caught more of them. No conntrack or netfilter option differs between the two configs.
- **Pre-existing:** `smartmontools.service` fails at boot on both kernels (SD card).
- **`rpi-eeprom-update.service`** ran and reported normally on every hardened boot.

## EEPROM update from the hardened kernel

Done at the end of H2 (20:00Z), from the hardened kernel under `lockdown=integrity`:

1. **Pre-checks:**
   - `/dev/spidev10.0` was bound to `spidev`;
   - `flashrom` probed the chip: Winbond W25Q16.V, 2 MB;
   - the bootloader config read from the device tree (`blconfig` nvmem) matched the stock read;
   - a full read-back matched the read-back taken on stock before the soak.
2. **The update:** `rpi-eeprom-update -f /usr/lib/firmware/raspberrypi/bootloader-2712/default/pieeprom-2026-09-25.bin`. It flashed immediately through `flashrom` over `spidev10.0`: `VERIFY: SUCCESS`, `UPDATE SUCCESSFUL`. No files were left in `/boot/firmware`, and the stock boot files did not change.
3. **Read-back:** differs from the Phase 0 image in 12 bytes, all inside the two `updatetime` records (one per bootloader copy). They hold 2026-11-04 ~08:09Z before and 2026-11-05 20:00:07Z after: the time of this flash. Everything else is byte-identical, and the embedded config equals stock.
4. **Next boot:** the plain reboot into stock (S2) came up in 61 s. The device tree's `chosen/bootloader/update-timestamp` reads 1793908807 (the new `updatetime`), and `build-timestamp` reads 1790351949 (the 2026-09-25 release). The bootloader that booted S2 was the image written from the hardened kernel.

It re-flashed the current version rather than a newer one. A real version change, 2026-09-25 → 2026-10-30, became available during the soak. On every boot `rpi-eeprom-update.service` (`-s -a`) skipped it on purpose: silent updates only apply below a minimum version (`current 1790351949 >= min 1746713597`). It is still pending; see [Follow-ups](#follow-ups).

## Incidents

None.

- **Reboots:** 5 (4 trial boots, 1 back to stock). SSH was back in 61–66 s each time, and Tor bootstrapped 24–50 s after boot.
- **`verify`:** `fails=0` on all four trial boots, and every one was confirmed. The dead-man never fired.
- **Network errors:** no `macb` TX timeouts, `NETDEV WATCHDOG` messages, or other kernel errors. No softnet drops and no NIC rx/tx drops. One softnet "squeeze" in H2 (a NAPI poll that ran out of budget), and none elsewhere.
- **Retransmissions:** TCP retransmissions were 0.5–0.9% of segments on hardened and 0.6–1.4% on stock.
- **`fq` drops:** on both kernels, from fq's own limits (see [TX timeouts and drops](#tx-timeouts-and-drops)).
- **One false alarm.** The soak's watcher alerted at 16:07Z, 7 minutes into H2. It had counted boot-time lines: `bcm2712-iommu … DEBUG_INFO` matched its `BUG` pattern. They showed up because journalctl's `--since` seeks by journal order: once timesyncd stepped the clock, kernel lines stamped earlier still come out after that point. Fixed in the watcher (`BUG:` / `kernel BUG`). Not a kernel event.

## Recommendations for Phase 5

1. **Ship the hardening as built.** No intent change:
   - `init_on_free=1`;
   - full `PREEMPT` with `PREEMPT_DYNAMIC`;
   - `DEBUG_LIST=y` with `LIST_HARDENED=y`.

   Budget about +11% Tor CPU and +15% whole-relay CPU per relayed byte, and about +30% in the kernel's network path.
2. **Go ahead with Phase 5 after review.** In order:
   1. Publish the pi5 release.
   2. On this relay, install the meta, then run `try`, `verify` and `confirm`.
   3. Run `promote`.
   4. Run the week the rollout table asks for.

   Keep re-applying the CVE-2026-98432 mitigation after every boot until it is made persistent. After `promote`, any reboot boots hardened, including a watchdog reboot.
3. **Apply the pending bootloader update (2026-09-25 → 2026-10-30) from the hardened kernel after `promote`,** with `rpi-eeprom-update -a`. This soak re-flashed the same version. That proved the write path, but not a version change.
4. **Watch during the week:**
   - `macb` TX timeouts and `NETDEV WATCHDOG` (`journalctl -k`);
   - unplanned reboots;
   - CPU0 softirq share, with RPS to be reconsidered above ~25%.

   Node_exporter already exports all three. The fleet automation's upgrades restart Tor, so its restarts are expected noise, not kernel events.

## Follow-ups

- **`unredacted-rpi5-boot status` reports a false change after `revert`.** `guarded` writes `# <time> after: $*` as the baseline's header. For `revert_files`, `$*` includes the whole multi-line `config.txt` ([unredacted-rpi5-boot:312](../../packages/unredacted-rpi5-boot/unredacted-rpi5-boot)). `status` keeps every line not starting with `#`, so it lists `removed` entries that don't exist. Display only: package removal compares against `stock-at-install.sha256` and was clean. Fix: write only the command name, or one line, into the header.
- **The defaults package came from the amd64 release.** The pi5 draft has no `unredacted-hardened-defaults`, so the soak installed the amd64 release's package (arch `all`). Its description reads "Pulled in by linux-image-hardened-unredacted-amd64" ([build-debs.sh:634](../../build/build-debs.sh) fills in the flavor that built it). Harmless, but decide which release a pi5 user's apt resolves it from before publishing.
- **Raw data** stays on the relay in `/root/phase4` (115 MB: samples, per-boot journals, perf data, step logs, EEPROM read-backs). Delete it when no longer needed.
